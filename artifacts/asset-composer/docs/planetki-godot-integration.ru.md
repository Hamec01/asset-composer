# Asset Composer → Planetki: схема интеграции

Дата обследования: 2026-10-09. Игра: `E:/Planetki`. Это проект интеграции после чтения кода, а не отчёт о выполненном подключении. Игровые файлы не изменялись.

## Что уже работает в игре

- `src/simulation/citizen_npc.gd`: CitizenNPC — RefCounted, а не Node2D. Есть citizen_id, seed_val, gender, age, cohort, race_id, job_id, workplace_id, state, task_id, cargo_type/amount, facing_dir, equipment и equipped_tool. `set_job()` меняет профессию, сбрасывает кэш изображения и прерывает часть рабочих состояний. Сохранение уже переносит идентичность, профессию, экипировку и инструмент.
- `src/map/character_texture_manager.gd`: готовый портрет выбирается по профессии, расе, полу и seed. Индивидуальные глаза/волосы/нос по слотам сейчас не хранятся.
- `src/map/world_map_view.gd`: жители рисуются вручную через CanvasItem; сортировка по положению уже общая с объектами мира. `_get_citizen_action_texture()` заменяет жителя общими спрайтами лесоруба, охотника и воина. Есть дополнительные процедурные инструменты и эффекты.
- `src/simulation/hero_animations.gd`: отдельный отрисовщик короля, собственные лист и таблица кадров; разовые действия используют sim_time_total. Контроллер героя уже вызывает play() при действиях.
- `src/core/unit_animation_manager.gd`: SpriteFrames для военных юнитов; это отдельный путь от жителей поселения.
- `src/simulation/professions/`: реальные поведения лесоруба, охотника, добытчика, ремесленника и скорняка; часть других профессий остаётся в общей симуляции. Лесоруб получает физический инструмент из лагеря, дерево теряет запас, груз доносится до склада.
- `src/combat/equipment_db.gd`: игровые характеристики, оружие, броня, рецепты. `src/core/item_texture_manager.gd`: отдельный каталог иконок.
- Возрастные группы игры: child до 13 включительно, youth 14–17, adult 18–45, elder 46+. В Composer подросток называется teen: требуется явное соответствие youth → teen.
- `project.godot` указывает Godot 4.7; исполнение проекта в рамках обследования не запускалось.

## Главное решение

Основной экспорт для жителей стратегии — модульный пакет. Готовый цельный PNG-лист остаётся отдельным режимом для неизменяемых персонажей и предпросмотра.

Идентичность жителя отделена от профессии: тело, лицо, волосы, шрамы, пол, возраст и индивидуальная подгонка сохраняются; смена профессии выбирает допустимую одежду и доступное снаряжение, а смена задания — действие. Назначение профессии само по себе не создаёт топор или броню в инвентаре.

Для первой версии рекомендуется компилировать визуальные данные существующим evaluateExportScene(), а не заново реализовывать в GDScript все правила Composer. В пакет входят общие текстуры и повторно используемые таблицы поз/порядка слоёв. Параметры подгонки и зависящие от комбинации деталей эффекты обязаны участвовать в компиляции или иметь явно поддержанный runtime-эквивалент. Одних матриц костей недостаточно: рот, моргание, маски бород, скрытие волос под шлемом, глубина и деформация вычисляются отдельно.

## Контракт пакета, версия 1

Предлагаемая папка игры: `res://Assets/composer/<pack_id>/`.

| Файл/каталог | Содержимое |
| --- | --- |
| manifest.json | format_version, pack_id, revision, типы объектов, зависимости, capabilities, путь к текстурам и данным |
| textures/ | PNG-атласы без потери исходного качества, явные области обрезки и отступы против протекания соседних пикселей |
| rigs/ | Семейства скелета, система координат, масштаб мира, точка опоры на земле, крепления слотов |
| appearances/ | Стабильные ID деталей, допустимые пол/возраст, рецепты внешности, индивидуальная подгонка, правила скрытия |
| items/ | ID рисунка, слот, привязки, локальная геометрия, иконка, визуальные теги совместимости; без игровых характеристик |
| clips/ | Стабильный action_id, fps, длительность, цикл, скомпилированные позы, порядок деталей, варианты лица и маркеры |
| bindings/planetki.json | Соответствия игровых предметов, профессий, задач, возрастов и действий визуальным ID |
| examples/ | Пример героя и жителя, одежда, инструмент, сценарии смены профессии |

Матрицы: явный порядок `[a,b,c,d,tx,ty]`, координаты в пикселях Composer, положительная ось Y вниз; пример преобразования в Transform2D и тест зеркального направления. Масштаб мира и ground pivot задаются данными, не угадываются по границе картинки. Не применять одновременно возрастное уменьшение Composer и старое уменьшение char_size в игре.

ID не зависят от русского названия или имени файла. На повторном экспорте они сохраняются. Проверка пакета выявляет отсутствующие ссылки, несовместимое семейство, неизвестную версию и неподдержанные возможности. В старом сохранении внешность генерируется один раз детерминированно из citizen_id/seed_val и записывается. Обновление пака не должно случайно перегенерировать лица.

Первый профиль ограничить `chibi_token_v1`. Для других объектов разрешать статический PNG или запечённую последовательность. Произвольные сетки, веса, IK и составные маски нельзя объявлять поддержанными до реализации и проверки: экспорт должен предложить запекание или назвать ограничение.

## Адаптер игры

Предлагаемые модули:

- `ComposerPackRegistry`: проверка версии, загрузка и кэш общих текстур/таблиц, поиск пакета по ID; импорт JSON через FileAccess, текстур-ресурсов через ResourceLoader.
- `CitizenVisualResolver`: читает состояние реального CitizenNPC и выдаёт appearance, equipment, action, phase, facing. Не меняет экономику, назначения и здоровье.
- `ComposerCitizenRenderer`: рисует скомпилированные детали в существующем world_map_view; поддерживает тот же результат для портрета. Старый renderer остаётся для жителей без поддержанного пакета.
- `PlanetkiVisualBindings`: централизованные соответствия игровых ID, без проверок русских названий и размножения match по UI.

Не создавать отдельное дерево узлов для каждой кости каждого жителя по умолчанию: сохранить существующую массовую отрисовку и проверить производительность. Общие данные кэшируются по pack/revision/rig/appearance/equipment; у жителя остаются ссылки и небольшое состояние воспроизведения. Отдельная сцена предпросмотра допустима для карточки и отладки.

Приоритет действий: смерть → явное разовое действие/бой → активная работа → переноска → движение/бегство → разговор/эмоции → отдых → idle. Фаза привязана к времени начала конкретного действия, а не к единому anim_time для всех жителей. Пауза и скорость симуляции учитываются явно. Разовые клипы доходят до конца и не перезапускаются каждый кадр.

## Привязки на текущем коде

| Игровой источник | Визуальное поведение |
| --- | --- |
| MOVING_TO_WORK, GOING_HOME, непустой path | walk; инструмент только из реального equipped_tool/equipment |
| FLEEING / FLEEING_HOME | run либо поддержанный вариант бегства |
| WORKING + chop_tree | axe_chop/chop; топор из equipped_tool |
| WORKING + mine_stone / mine_ore | действие добычи, кирка по привязке доступного игрового инструмента |
| WORKING + craft | действие по реальной мастерской: forge/pottery/carpenter и т.п.; текущий craftsman общий |
| WORKING + tan_hides | действие выделки/шитья, с учётом доступных реквизита и рабочего места |
| CARRYING + cargo_amount > 0 | carry, груз по cargo_type; при нулевом грузе скрыть |
| ATTACKING | удар по реальному weapon, для лука — bow_attack; не определять оружие только по job_id |
| TALKING, CELEBRATING, MOURNING | разговор, танец/радость, скорбь с соответствующей мимикой |
| is_alive == false | death, удержание последней позы; захороненный скрыт |
| cohort youth | возраст Composer teen |

Названия в этой таблице описывают привязку. Конкретный action_id проверяется по каталогу при экспорте, отсутствующие действия не замещаются случайным клипом. Станок, печь, дерево и могила — объекты мира: не добавлять их к каждому жителю поверх уже существующей постройки. Предмет на земле, в инвентаре и в руках использует один игровой ID с разными визуальными представлениями.

Правило двуручного оружия и щита обеспечивается в игровой экипировке; отрисовщик дополнительно отклоняет невозможную комбинацию. Урон, прочность и производство остаются в EquipmentDB и симуляции. Визуальный ID присваивается через таблицу, например work_axe → рисунок топора; разные металлы могут ссылаться на разные изображения, пока такие изображения действительно есть в пакете.

## Синхронизация труда и боя

Сейчас рубка уменьшает ресурс по work_timer с интервалом 4.5–6 секунд, а анимация выбирается глобальным временем. При подключении добавить явное начало рабочего цикла, его длительность и момент контакта. Визуальный контакт должен совпадать с существующей добычей, а не выдавать дополнительную древесину.

Маркеры Animation X-Ray — диагностические фазы, их нельзя автоматически считать игровыми hit/release событиями. Нужны отдельные семантические маркеры contact/release/complete. При переносе событий на эти маркеры гарантия — ровно одно применение за цикл, включая большой delta, ускорение, паузу, загрузку и уход цели. Симуляция работает и без renderer; уход жителя за экран не останавливает работу.

## Удобный экспорт из Composer

Кнопка «Экспортировать → Godot / Planetki»:

1. Выбрать объекты, детали, предметы и клипы; выбрать «Модульный житель» или «Готовые кадры».
2. Назначить/проверить игровые привязки и показать недостающие инструменты/клипы.
3. Указать качество текстур и масштаб мира; показать размер пакета.
4. Получить ZIP в веб-версии. В Electron — выбрать папку проекта Godot и писать только внутрь Assets/composer/<pack_id> с проверкой manifest, не изменяя посторонние файлы.
5. Плагин Godot импортирует пакет и показывает проверочный экран. Повторный экспорт обновляет тот же pack_id; проектные привязки игры хранятся отдельно от генерируемых файлов.

Встроенная инструкция должна включать: первый импорт, привязку инструмента к игровому ID, смену профессии, сохранение лица, обновление пакета и исправление отсутствующего клипа. Для собранной игры явно включить JSON пакета в экспорт либо преобразовать данные плагином в Godot-ресурсы; успешная загрузка только в редакторе недостаточна.

## Порядок реализации и проверка

1. Контракт v1, валидатор и экспорт одного взрослого чиби с idle/walk/chop/carry, топором и двумя одеждами. Сравнить кадры Composer и Godot.
2. Runtime и адаптер одного жителя: тот же человек становится лесорубом, реально получает топор, рубит, несёт дрова, меняет профессию. Старые портреты остаются резервным путём.
3. Сохранение внешности и обновление пакета; дети, подростки, пожилые и мимика. Сохранить выбранные детали и подгонку, не дублировать возрастный масштаб.
4. Остальные реальные рабочие задачи, оружие, щит, предметы на земле и в инвентаре, отдельная привязка короля.
5. UI экспорта, импортёр, инструкция/FAQ и проверка собранной игры.

Приёмка: оба направления; волосы/шлем, борода/рот, двуручное/щит; нет инструмента — нет картинки инструмента; новый job не меняет лицо; предмет не появляется из воздуха; груз исчезает после сдачи; цикл не удваивает добычу/урон; пауза/ускорение; сохранение и загрузка старой и новой игры; отсутствие пакета; обновление revision; множество видимых жителей и отдаление камеры. Измерить память и время кадра на целевом ПК, не обещать число жителей без замеров.
